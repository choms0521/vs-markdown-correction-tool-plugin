P5 — Diff 적용 (Diff & WorkspaceEdit)

Phase 5 detailed plan · HunkComputer + DiffPresenter + HunkApprover + WorkspaceEditBuilder · 마스터 계획 docs/plans/vscode-md-review-plan.md 분해본 · 2026-05-15 작성

1. 개요

본 phase는 P4 LLMOrchestrator가 반환한 수정 마크다운을 사용자에게 검토 가능한 형태로 제시하고, hunk 단위 승인을 거쳐 원본 .md에 반영하는 마지막 절반을 마무리한다. 핵심은 (1) 라인 단위 LCS diff로 hunk 분해, (2) vscode.diff 명령으로 좌우 비교 표시, (3) QuickPick UI로 hunk별 accept/reject 수집, (4) 승인된 hunk만 WorkspaceEdit으로 적용 — Human-in-the-loop 원칙(spec Principle 5)을 만족한다.

GoalP4 응답 마크다운을 원본과 라인 단위 diff로 분해 → vscode.diff editor 좌우 표시 → QuickPick으로 hunk별 승인 → 승인된 hunk만 WorkspaceEdit으로 원본에 반영. 자동 적용 없음.
Side / Outvsce 패키징(P6), platform-specific vsix(P6), inline accept 버튼(F-2 future), 다중 응답 큐(future).

2. RALPLAN-DR 요약

2.1 Principles (3~5)

  1. Human-in-the-loop은 양보 불가 — 자동 적용은 spec Principle 5의 invariant이다. 어떤 단축도 사용자 명시 승인을 우회할 수 없다.
  2. 의존성 최소화 — P4의 cost-guard 정신을 P5에도 적용한다. line LCS는 50~80 LOC로 충분하므로 외부 diff 패키지 추가는 정당화되지 않는다.
  3. 인덱스 안전성 — 다중 hunk 적용 시 line index shift 회피. WorkspaceEdit은 라인 내림차순(아래부터 위로) 적용한다.
  4. VSCode native UX 우선 — diff editor는 VSCode 내장 그대로 사용. hunk 승인은 QuickPick으로 보조(주 진입점).
  5. 경계 검증 — hunk 객체는 zod 기반 zero-trust(다만 내부 데이터 흐름이므로 schema는 가벼움), QuickPick 결과는 enum으로 정규화.

2.2 Decision Drivers (Top 3)

2.3 Viable Options (≥2)

옵션설명ProsConsDriver 부합
Option A
외부 diff npm 패키지		 diff(MIT, jsdiff) 채택. structuredPatch로 hunk 생성, applyPatch로 적용. 검증된 라이브러리, word-level까지 확장 가능, hunk parsing 무료. ~50KB 추가, transitive 0건이긴 하나 cost-guard 정신 위반. line diff만 필요한 우리 use case 대비 과적. D1 OK / D2 위반 / D3 OK
Option B (선택)
내장 LCS line-diff		 LCS 길이 표(O(N·M)) → backtrack → line-level edit script → 인접한 edit을 hunk로 그룹핑. 의존성 0건, 50~80 LOC, 우리 use case에 fit. mocha 단위 테스트 단순. word/char level 미지원. 단, AC는 line-level로 충분. D1 OK / D2 OK / D3 OK
Option C
vscode.diff만 + 전부 적용/거부		 hunk 분해 없이 사용자가 diff editor를 본 뒤 "전체 적용 / 전체 거부"만 선택. 코드 가장 단순(20 LOC). AC-11(hunk별 승인) 위반. spec Principle 5의 정신과 어긋남. D1 위반 → 즉시 기각

2.4 선택 근거

채택: Option B (내장 LCS line-diff) Option C는 D1을 정면 위반하므로 자동 기각. Option A는 D2(의존성 0건)와 충돌. Option B는 line LCS 50~80 LOC로 우리 use case에 정확히 부합하며 세 driver를 모두 만족한다. word-level diff는 P5 non-goal이므로 LCS의 line-level 한계는 영향 없음. 단, Hunk 인터페이스를 line-range + replacement string으로 정의하여 후일 word-level로 확장 가능한 추상화는 유지한다.

5. Critical Code Specs

5.1 HunkComputer — line LCS

export interface Hunk {
  id: string;
  // 원본의 라인 범위 [startLine, endLineExclusive). endLineExclusive === startLine 이면 순수 insert.
  beforeRange: { startLine: number; endLineExclusive: number };
  beforeText: string; // 원본 라인들을 \n으로 join (마지막 \n 미포함)
  afterText: string;  // 교체 라인들. afterText === '' 이면 순수 delete.
  kind: 'replace' | 'insert' | 'delete';
}

export class HunkComputer {
  compute(original: string, revised: string): Hunk[] {
    // 1. EOL 정규화 (\r\n → \n). 입력 본문은 그대로 두고 비교용만 정규화.
    const origLines = splitLines(normalizeEol(original));
    const revLines  = splitLines(normalizeEol(revised));

    // 2. LCS DP. dp[i][j] = 두 prefix의 LCS 길이.
    const n = origLines.length, m = revLines.length;
    const dp: number[][] = Array.from({length: n+1}, () => new Array(m+1).fill(0));
    for (let i=1; i<=n; i++)
      for (let j=1; j<=m; j++)
        dp[i][j] = origLines[i-1] === revLines[j-1]
          ? dp[i-1][j-1] + 1
          : Math.max(dp[i-1][j], dp[i][j-1]);

    // 3. backtrack → edit script ('eq' | 'add' | 'del')
    const ops: EditOp[] = [];
    let i = n, j = m;
    while (i>0 || j>0) {
      if (i>0 && j>0 && origLines[i-1] === revLines[j-1]) { ops.push({k:'eq', a:origLines[i-1]}); i--; j--; }
      else if (j>0 && (i===0 || dp[i][j-1] >= dp[i-1][j])) { ops.push({k:'add', a:revLines[j-1]}); j--; }
      else { ops.push({k:'del', a:origLines[i-1]}); i--; }
    }
    ops.reverse();

    // 4. 인접한 add/del을 single hunk로 그룹핑.
    return groupHunks(ops);
  }
}

// groupHunks: 'eq' 시퀀스를 경계로 add/del run을 hunk로 묶는다.
// 각 hunk에 stable id (h0, h1, ...) 부여. 원본 라인 인덱스 기준 startLine 계산.
function groupHunks(ops: EditOp[]): Hunk[] { /* ... */ }
설계 의도 LCS는 O(N·M)이지만 검토용 마크다운은 일반적으로 ≤ 1000라인이므로 1ms 미만이다. 후일 word-level이 필요하면 LCS 결과의 add/del 페어를 word-LCS로 재분해할 수 있는 확장점이 있다 (현재는 line-level만).

5.2 DiffPresenter — vscode.diff 래퍼

export interface DiffPresenterDeps {
  openTextDocument(options: { content: string; language: string }): Promise<{ uri: vscode.Uri }>;
  executeCommand(command: string, ...args: unknown[]): Promise<unknown>;
}

export class DiffPresenter {
  constructor(private readonly deps: DiffPresenterDeps) {}

  async present(originalUri: vscode.Uri, revisedText: string, title: string): Promise<vscode.Uri> {
    // 1. 임시 untitled doc 생성 (메모리 기반, 디스크 미반영)
    const doc = await this.deps.openTextDocument({ content: revisedText, language: 'markdown' });
    // 2. VSCode 내장 diff 명령 발화. 좌: 원본 (read-only는 보존), 우: revised untitled doc
    await this.deps.executeCommand('vscode.diff', originalUri, doc.uri, title, { preview: true });
    return doc.uri;
  }
}

5.3 HunkApprover — QuickPick 다중 선택

export interface QuickPickBridge {
  showMultiPick(
    items: QuickPickItemLite[],
    options: { title: string; placeHolder: string },
  ): Promise<QuickPickItemLite[] | undefined>; // undefined = 취소
}

export interface QuickPickItemLite {
  id: string;
  label: string;
  detail?: string;
  picked?: boolean;
}

export class HunkApprover {
  constructor(private readonly bridge: QuickPickBridge) {}

  async askApprovals(hunks: readonly Hunk[]): Promise<Set<string>> {
    if (hunks.length === 0) return new Set();
    const items: QuickPickItemLite[] = hunks.map((h) => ({
      id: h.id,
      label: formatHunkLabel(h),   // "H1: L12~14 -2 +3"
      detail: formatHunkPreview(h), // "- old line\n+ new line" (truncated)
      picked: true,                // 기본 전체 선택 (안전한 default = 사용자가 거부할 것만 해제)
    }));
    const selected = await this.bridge.showMultiPick(items, {
      title: '적용할 hunk 선택',
      placeHolder: 'Space로 토글, Enter로 확정, Esc로 전체 취소',
    });
    if (!selected) return new Set();
    return new Set(selected.map((s) => s.id));
  }
}
UX 결정: 기본 전체 선택 LLM 응답을 신뢰하는 default-on 정책. 사용자는 거부할 hunk만 토글 해제하면 된다. 반대로 default-off도 검토했으나 hunk가 많을 때(예: 10개) 모두 수동 체크하는 부담이 크다. 거부가 더 드문 작업으로 가정.

5.4 WorkspaceEditBuilder — 내림차순 applyEdit

export interface EditApplier {
  applyEdit(edit: vscode.WorkspaceEdit): Thenable<boolean>;
}

export class WorkspaceEditBuilder {
  constructor(private readonly applier: EditApplier, private readonly editFactory: () => vscode.WorkspaceEdit) {}

  async buildAndApply(
    uri: vscode.Uri,
    hunks: readonly Hunk[],
    approvedIds: ReadonlySet<string>,
  ): Promise<{ appliedCount: number }> {
    const approved = hunks.filter((h) => approvedIds.has(h.id));
    if (approved.length === 0) return { appliedCount: 0 };

    // 핵심: 라인 내림차순 → 위쪽 hunk 적용 시 아래 hunk의 line index가 shift되지 않도록.
    const ordered = [...approved].sort((a, b) => b.beforeRange.startLine - a.beforeRange.startLine);

    const edit = this.editFactory();
    for (const h of ordered) {
      const range = new vscode.Range(
        h.beforeRange.startLine, 0,
        h.beforeRange.endLineExclusive, 0,
      );
      // afterText는 EOL을 \n으로 통일했으므로 그대로 사용. 빈 문자열이면 순수 delete.
      const replacement = h.afterText.length > 0 ? h.afterText + '\n' : '';
      edit.replace(uri, range, replacement);
    }

    const ok = await this.applier.applyEdit(edit);
    if (!ok) throw new Error('applyEdit가 false를 반환');
    return { appliedCount: approved.length };
  }
}

5.5 MarkdownReviewEditor — submit 핸들러 P5 전환

session.attachSubmitHandler(async (comments) => {
  try {
    const result = await orchestrator.submit(document.getText(), comments);
    this.output.appendLine(`[mdReview] submit ok uuid=${result.uuid} bytes=${result.markdown.length}`);

    const hunks = this.hunkComputer.compute(document.getText(), result.markdown);
    this.output.appendLine(`[mdReview] hunks=${hunks.length}`);
    if (hunks.length === 0) {
      await vscode.window.showInformationMessage('mdReview: 변경 사항이 없사옵니다.');
      return;
    }

    const presenter = this.makeDiffPresenter();
    await presenter.present(document.uri, result.markdown, `mdReview: ${basename(document.uri.fsPath)}`);

    const approver = this.makeHunkApprover();
    const approved = await approver.askApprovals(hunks);
    if (approved.size === 0) {
      await vscode.window.showInformationMessage('mdReview: 적용된 hunk가 없사옵니다.');
      return;
    }

    const builder = this.makeWorkspaceEditBuilder();
    const { appliedCount } = await builder.buildAndApply(document.uri, hunks, approved);
    await vscode.window.showInformationMessage(
      `mdReview: ${appliedCount}개 hunk를 본문에 반영하였사옵니다. 저장(Cmd+S)을 잊지 마시오.`,
    );
  } catch (e) {
    const msg = e instanceof Error ? e.message : String(e);
    await vscode.window.showErrorMessage(`mdReview submit 실패: ${msg}`);
  }
});

7. Diff 라이브러리 선택 근거 (추가 ADR)

항목외부 diff (jsdiff)내장 LCS (선택)
코드 크기~50KB (transitive 0)~80 LOC
line-level diff✓ diffLines✓ LCS 기반
word-level diff✓ diffWords✗ (P5 non-goal)
hunk 자동 생성✓ structuredPatch인접 add/del 그룹핑 (~20 LOC)
EOL 정규화옵션 제공수동 (normalizeEol 헬퍼)
D2(의존성 0건)위반준수
유지보수 부담외부 변경에 노출내부 통제 가능
결단 P5의 실제 요구는 line-level diff + hunk별 적용이며 word-level은 명시적 non-goal이다. 외부 라이브러리는 80% unused capability를 안고 가는 셈이다. 80 LOC LCS는 mocha로 단위 테스트 가능하고 우리 use case와 1:1 fit이다. 향후 word-level 요구가 발생하면 그 때 jsdiff 도입 또는 LCS의 add/del 페어를 word-LCS로 재귀 분해하여 점진적 확장 가능.

9. Risks & Mitigations

#위험가능성영향완화책임 phase
R5-1 EOL 차이로 hunk 잘못 분해 (Windows \r\n 원본 + LLM의 \n 응답) 중 중 normalizeEol 헬퍼로 비교만 정규화. 출력 본문은 OS native EOL 보존하지 않고 \n 통일 (revised는 LLM에서 받은 그대로). 향후 사용자 옵션화 검토. P5 Day 1
R5-2 다중 hunk applyEdit 인덱스 shift 중 높음 WorkspaceEditBuilder가 startLine 내림차순 정렬 후 적용. 단위 테스트로 회귀 방지 ("내림차순 적용 순서 검증"). P5 Day 1.5
R5-3 QuickPick 취소를 사용자가 "전체 적용"으로 오해 중 중 placeHolder에 "Esc로 전체 취소" 명시. Esc → empty Set → 토스트 "적용된 hunk가 없사옵니다"로 명확한 피드백. 본문 unchanged. P5 Day 1.5
R5-4 사용자가 diff editor만 닫고 QuickPick은 무시 → 본문 변경 없이 종료 낮 낮 QuickPick이 main control. diff editor 닫혀도 QuickPick 살아 있음. 사용자가 다시 QuickPick에 응답하면 정상 흐름. 의도된 동작. P5 Day 1.5
R5-5 매우 큰 응답(>10,000 라인)에서 LCS O(N·M) 성능 저하 낮 낮 마크다운 리뷰 use case는 ≤ 1000라인. 10,000라인이면 100MB DP 표 → 메모리 압박. 현재는 cap 없음. P6에서 입력 길이 가드 검토. P6 follow-up
R5-6 WorkspaceEdit이 readonly 파일에 실패 낮 낮 applyEdit이 false 반환 → throw → catch → showErrorMessage. 사용자가 파일 readonly 해제 후 재시도. P5 Day 1.5+
